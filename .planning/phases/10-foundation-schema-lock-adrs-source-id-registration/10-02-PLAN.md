<objective>
Add additive `pub id: Option<String>` field to the `Holiday` struct (`crates/amlich-core/src/holidays.rs:14-25`) and propagate the stable id from `data/holidays/lunar-festivals.json` through the data layer. Sóc/Vọng generated entries, Thanh Minh, and any creation site without a source id leave `id: None`.

Purpose: Phase 11's ritual matcher needs `Holiday.id` to join `RitualEntry.event_keys[]` of kind `{"kind":"holiday_id","value":"<id>"}` against the day's active holidays. Without this field, the matcher cannot resolve festival rituals deterministically. FND-06 also requires v1.4 fixture round-trip compatibility — verified additive because `Holiday` is internal (not serialized today).

Output:
- `LunarFestivalData` gains `pub id: String` (verified absent in current struct).
- `Holiday` gains `pub id: Option<String>` as first field.
- All `Holiday` creation sites in `holidays.rs` populate or default `id`.
- Unit test confirms `get_vietnamese_holidays(2024)` returns an entry with `id == Some("tet-nguyen-dan")` and another with `id == None` (for Mùng 1/Rằm).

Discovery decision documented in plan rationale: NO `Serialize`/`Deserialize` derive added to `Holiday` in Phase 10. `Holiday` currently derives only `Debug, Clone`. FND-06 requires the field exists and is populated; the INT-05 round-trip test (Phase 15) targets `DaySnapshot` JSON, not `Holiday` directly. Adding serde to `Holiday` would be a scope-expansion change reaching DTO conversion code; defer to Phase 15 where DTO surfaces are touched.
</objective>
