## Executive Summary

The regression is localized to `get_days_to_nearest_tiet_khi()` in `crates/amlich-core/src/tietkhi.rs`.

Current implementation mixes Julian Day arithmetic with invalid year/day reconstruction (`jd / 365`, synthetic month/day) and produces impossible deltas (for example `1722495`), which directly causes the five failing tests:

- `test_after_returns_positive`
- `test_before_returns_negative`
- `test_equidistant_prefers_after`
- `test_exact_match_returns_zero`
- `test_term_positions_in_year`

The safest fix path is to replace synthetic term search with a real nearest-boundary scan using existing term boundary detection (`get_all_tiet_khi_for_year`) across adjacent years.

---

## Root Cause

1. `get_days_to_nearest_tiet_khi()` does not compute actual term boundaries.
2. It fabricates candidate term dates from approximate day offsets, then converts those with `jd_from_date` using invalid month/day values.
3. This breaks sign and distance guarantees required by TK-02..TK-05.

---

## Recommended Fix Strategy

1. Convert input JD to Gregorian year (`jd_to_date`).
2. Build a candidate list from `get_all_tiet_khi_for_year(year - 1..=year + 1, 7.0)`.
3. De-duplicate candidate JDs, sort ascending, find nearest before/after.
4. Return signed nearest distance with stable tie policy (prefer after, matching current tests and plan intent).
5. Keep implementation deterministic and free of external dependencies.
