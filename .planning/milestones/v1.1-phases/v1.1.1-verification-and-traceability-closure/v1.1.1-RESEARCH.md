## Summary

This phase is a documentation-and-governance closure phase, not a feature implementation phase. The key technical decision is to treat verification as a first-class artifact with strict source-of-truth behavior: requirement claims are valid only when backed by fresh command evidence and file-level references in a canonical phase verification file.

The existing v1.1 summaries provide strong implementation hints but are insufficient for audit closure because they are narrative and currently lack machine-readable requirement completion metadata. The missing artifact pattern can be closed by creating one `v1.1-VERIFICATION.md` with per-requirement status and by adding `requirements-completed` frontmatter to `v1.1-01..03-SUMMARY.md`.

Status reconciliation should be downstream of verification outcomes. Because current tietkhi tests are red, TK requirements should be explicitly marked blocked/partial in verification outputs and propagated consistently into `ROADMAP.md` and `STATE.md` without claiming milestone completion.

**Primary recommendation:** Build a single canonical verification ledger first, then drive all status and traceability updates from that ledger.

## Architecture Patterns

### Pattern 1: Canonical verification artifact drives status
**What:** `v1.1-VERIFICATION.md` contains requirement matrix, evidence links, and gate status.
**When to use:** Any milestone with multiple execution summaries and acceptance ambiguity.

### Pattern 2: Three-source requirement closure
**What:** Requirement status closes only when plan intent, summary completion metadata, and verification evidence agree.
**When to use:** Requirement-level audit and machine-readable traceability updates.

### Pattern 3: Explicit blocked state for red gates
**What:** If tests fail, mark requirement/milestone blocked rather than complete.
**When to use:** Implementation exists but acceptance gate is not green.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Requirement traceability inference | Implicit interpretation from narrative summaries | Explicit `requirements-completed` frontmatter + central matrix | Deterministic, machine-readable audits |
| Status reconciliation logic | Scattered ad hoc status notes | Single-source-of-truth propagation from verification file | Prevents roadmap/state drift |

## Common Pitfalls

### Pitfall 1: Marking requirements complete from implementation-only evidence
**What goes wrong:** Code exists, but acceptance gate fails.
**How to avoid:** Require fresh command output and mark as blocked/partial when red.

### Pitfall 2: Updating roadmap/state before verification is finalized
**What goes wrong:** Metadata contradicts final gate status.
**How to avoid:** Finalize verification ledger first, then reconcile status artifacts.

### Pitfall 3: Losing requirement granularity
**What goes wrong:** Group-level status hides individual requirement edge cases.
**How to avoid:** Keep per-ID status rows, even when summarizing by family.
