### 3. Tiết Khí Helper Functions

#### Current State

The `tietkhi.rs` module (376 lines) provides:
- `TIET_KHI: [SolarTermDef; 24]` — 24 solar term definitions
- `get_tiet_khi(jd: i32, time_zone: f64) -> SolarTerm` — Get current solar term for a Julian Day
- `get_all_tiet_khi_for_year(year, time_zone)` — Get all terms for a year

**Missing Functionality:** There's no existing helper to calculate "days to nearest Solar Term" — a common requirement for Đại Vận (Major Luck) calculations.

#### Implementation Approach

**Pattern:** Extend existing `tietkhi.rs` module with utility function. No new module needed.

**Recommended Function Signature:**

```rust
/// Get signed days to nearest Solar Term from given Julian Day
///
/// Returns negative value if nearest term is before input date,
/// positive if after, 0 if exactly on a term boundary.
///
/// # Arguments
/// * `jd` - Julian Day Number
/// * `time_zone` - Timezone offset (default: 7.0 for Vietnam)
///
/// # Returns
/// Signed integer difference in days
pub fn get_days_to_nearest_tiet_khi(jd: i32, time_zone: f64) -> i32 {
    // 1. Find most recent Solar Term with JD <= input JD
    // 2. Find next Solar Term with JD > input JD
    // 3. Calculate differences
    // 4. Return difference with smaller absolute value
    // 5. If on boundary, return 0
}
```

**Algorithm Design:**

1. **Linear Search Approach:** Since Tiết Khí occur every ~15 days, and we're searching within ±15 days of input date, linear search backward/forward from input JD is efficient.

   ```rust
   // Find most recent term
   let mut prev_jd = jd;
   while prev_jd > jd - 30 {  // Search 30 days back
       prev_jd -= 1;
       let term = get_tiet_khi(prev_jd, time_zone);
       // Detect term transition
   }

   // Find next term
   let mut next_jd = jd;
   while next_jd < jd + 30 {  // Search 30 days forward
       next_jd += 1;
       let term = get_tiet_khi(next_jd, time_zone);
       // Detect term transition
   }
   ```

2. **Optimization Consideration:** Linear search is acceptable because:
   - Search window is small (±15 days)
   - `get_tiet_khi()` is O(1) operation
   - Performance impact is negligible for day-level calculations

3. **Edge Cases:**
   - **Exact Boundary:** If input JD is exactly on a Solar Term, return 0
   - **Year Boundaries:** Handle Dec 31 → Jan 1 transitions correctly
   - **Far from Boundaries:** Should work correctly for any date in 2020-2030 range

**Architectural Considerations:**

1. **Function Placement:** Add to `tietkhi.rs` module (not `almanac/tietkhi.rs` since that doesn't exist). The module is at `crates/amlich-core/src/tietkhi.rs`.

2. **API Surface:** Public function (`pub fn`) — accessible from other modules. No DayFortune integration required for this phase (future feature for Đại Vận).

3. **Timezone Handling:** Accept `time_zone` parameter for consistency with existing `get_tiet_khi()` function.

**Data Verification Required:** No new data needed — pure algorithmic calculation using existing Solar Term logic.

### Q3: Empty Tàng Can Handling — Empty String vs Null vs Omitted?

**Question:** How should branches with empty hidden stems (子, 卯, 酉) be represented in JSON — as empty strings, null, or omitted fields?

**Recommendation:** **Use empty strings `""` for missing stems.**

**Reasoning:**
1. Fixed-size array `[&str; 3]` is more ergonomic than `Option<&str>`
2. JSON output is predictable: always 3 elements
3. Matches specification format (empty strings explicitly shown)
4. Simpler to consume in downstream code (no null checking needed)

**Decision:** Use `&'static str` for all fields, empty strings `""` for missing stems.
